## DEMO STEPS (15 minutes)

---

### 1. Introduction (2 minutes)

**Say:**
> "Teams struggle to get a quick, honest view of sprint health mid-sprint. JIRA has the data but the native board doesn't tell you *how likely* you are to finish or *which issues* are most at risk. Our tool pulls live data from JIRA and surfaces that in one place."

**Show:**
- The architecture diagram from `docs/UML_DIAGRAMS.md` (Deployment Diagram) — point to: JIRA Cloud → Spring Boot → React → Browser.
- The JIRA board in the other tab so the evaluator can see real data.

**Key points to state:**
- Single Spring Boot application, React frontend bundled inside the same JAR.
- No external AI API key — all analysis is deterministic heuristics, explainable at the viva.
- Deploys to Kubernetes; built and tested through Jenkins.

---

### 2. Dashboard Page (3 minutes)

**Navigate to:** `http://$(minikube ip):30080`

**Show and explain:**
1. **Health badge** — the coloured badge at the top (green = `HEALTHY`, amber = `WATCH`, red = `AT_RISK`).
   - Explain the thresholds: completion rate ≥ 80% and blocked ratio ≤ 20% → HEALTHY; rate ≥ 60% or blocked ratio ≤ 40% → WATCH; otherwise AT_RISK.
2. **Four metric cards** — Total Issues, Completed, In Progress, Blocked.
   - Point out the numbers and confirm they match the JIRA board tab.
3. **Completion percentage bar** — the filled bar shows story-point completion rate visually.
4. **Recommendations list** — bullet points generated by `SprintMetricsService.health()`.
   - If blocked > 0 you will see "Resolve N blocked issue(s) in today's standup."
5. **Refresh button** — click it; explain it calls `POST /api/v1/sprints/refresh` which invalidates the Caffeine cache; the next request re-fetches from JIRA.

---

### 3. Sprint Analysis Page (3 minutes)

**Navigate to:** Sprint Analysis tab in the sidebar.

**Show and explain:**
1. **Sprint selector dropdown** — populated from `GET /api/v1/sprints`; switch to a closed sprint to show it still works, then switch back to the active one.
2. **Story-point bar chart** — Recharts bar showing completed story points vs remaining. Point out the numbers match the metric cards.
3. **Workload-by-assignee table** — sorted by task count descending. Explain this comes from the `workloadByAssignee` map in the analysis response.
4. **Issue table** — paginated list with columns: Key (clickable), Summary, Status, Priority, Assignee, Story Points.
   - Point to a blocked issue row to connect it to the health badge count.

---

### 4. AI Insights Page (4 minutes)

**Navigate to:** AI Insights tab in the sidebar.

**Step 4a — Prediction:**

1. **Completion probability** — the large percentage number at the top. Walk through the formula:
   - H1 (progress-pace ratio): `completionRatio ÷ elapsedFraction`. Above 1.0 means ahead of pace.
   - H2 (blocked penalty): 5% per blocked issue, capped at 40%.
   - H3 (unassigned penalty): 3% per unassigned active issue, capped at 20%.
   - `probability = clamp(H1 − H2 − H3, 0.05, 0.98)`
2. **Trend badge** — `AHEAD`, `ON_TRACK`, or `BEHIND`. Explain the ±10% threshold against expected linear pace.
3. **Days remaining** — computed from sprint `endDate`.
4. **Insights and suggested actions** — generated bullet lists.

**Step 4b — Risk table:**

5. Point to the highest-risk issue (should be your blocked + unassigned one, score = 0.50).
   - Expand it and read the factors: "Issue is blocked" (+0.40), "No assignee" (+0.10).
   - Read the mitigations: "Escalate blocker in today's standup", "Assign immediately".
6. Explain the level thresholds: HIGH ≥ 0.65, MEDIUM ≥ 0.40, LOW > 0.25.
7. Confirm the table is sorted by risk score descending.

**Step 4c — Assignment recommendations:**

8. Point to the recommendations table for unassigned issues.
   - Read one row: Issue key, Recommended Assignee, Reason ("Least loaded member with N active task(s)"), Confidence %.
   - Explain the algorithm: iterate unassigned non-Done issues; for each, pick the team member with the smallest active task count; confidence = `max(0.40, 1.0 − load × 0.10)`.

## QUESTIONS TO PREPARE FOR

| Question | Key answer |
|----------|-----------|
| Why is the probability clamped to 0.05–0.98? | A sprint is never guaranteed to fail or to succeed; the bounds keep the output honest and avoid division-by-zero edge cases. |
| What happens if the JIRA API is unreachable? | `JiraAgileApiClient` throws `JiraApiException`; `ApiExceptionHandler` returns HTTP 500 with a JSON error body. The cache still serves the last successful response until TTL expires. |
| Why use Caffeine cache instead of a database? | The demo uses a single Minikube node. A short TTL (5 min) is sufficient for the classroom demo while avoiding JIRA rate limits. No persistent state is needed because JIRA is the system of record. |
| Why not use an LLM for the AI analysis? | Deterministic heuristics are explainable, have no API cost, and work without internet during the viva. The `SprintAIAnalyzer` is the right place to add an optional LLM call in production. |
| What is the story-points custom field? | `customfield_10016` is Atlassian's standard field for next-gen projects; the mapper also falls back to `customfield_10028` for classic projects. |
| Why `imagePullPolicy: IfNotPresent`? | We use `minikube image load` to push the image directly into Minikube's Docker daemon; there is no registry, so pulling would fail. `IfNotPresent` uses the loaded image. |
